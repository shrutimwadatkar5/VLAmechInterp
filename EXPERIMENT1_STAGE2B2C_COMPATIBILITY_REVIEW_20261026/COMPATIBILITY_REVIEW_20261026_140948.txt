  2) opentelemetry-exporter-otlp-common 0.66b1 requires
     opentelemetry-sdk~=1.45.1; installed 1.21.0.

Evidence gathered:
  - Repository grep: fastapi appears only in vla-scripts/deploy.py.
    There are no opentelemetry/otlp references in the repository.
  - Importing experiments.robot.openvla_utils.get_vla loads wandb but no
    fastapi or opentelemetry modules (checked via sys.modules).
  - The installed opentelemetry-exporter-otlp-common 0.66b1 has no installed
    reverse dependency; it is required by the 1.45.1 OTLP exporter, not by
    the installed 1.21.0 exporter.
  - opentelemetry-proto 1.45.1 requires protobuf>=5.0, while TensorFlow 2.15
    requires protobuf<5.0. Upgrading the OTel stack to satisfy fastapi 0.162
    would therefore conflict with TF 2.15.
  - fastapi 0.115.0 metadata has no opentelemetry requirement; 0.162.0 has an
    unconditional opentelemetry-api>=1.44.0 requirement.

Assessment:
  These conflicts are metadata-level and are not on the verified get_vla /
  prismatic / LIBERO import path. They remain real for vla-scripts/deploy.py
  and for any future resolver operation. They are NOT resolved in this stage.
  A later, separately approved evaluation could consider pinning an older
  FastAPI (e.g. 0.115.0) and/or removing the orphan
  opentelemetry-exporter-otlp-common, but neither was tested or applied here.

Expected changes:
  tensorflow-metadata: 1.21.0 -> 1.17.3
  Everything else: unchanged (protobuf 4.25.5, tfds 4.9.3, absl-py 2.5.1,
  googleapis-common-protos 1.62.0, all opentelemetry 1.21.0 packages,
  wandb 0.16.6, torch stack, transformers fork, dlimp, openvla-oft).

Why not 1.14.0:
  It cannot coexist with protobuf 4.25.5 (requires protobuf<4.21). Its only
  resolver-valid fallback downgrades protobuf to 3.20.3 and absl-py to 1.4.0,
  which is a larger and less desirable change.

Risks:
  - tensorflow-metadata 1.17.3 is older than 1.21.0; some APIs could differ.
    The import-level test passed, but full dataset construction was not run.
  - tensorflow-datasets leaves tensorflow-metadata unpinned, so a future
    `pip install -U` could reinstall 1.21.0 and reintroduce the shim
    dependency. A durable solution should keep the pin in future install
    commands or use an external constraints file. No repository file was
    changed in this stage.
  - pip check after installation is expected to still report the two
    FastAPI/OTel conflicts; it should not report any new tf-metadata/protobuf
    conflict.
  - The shim is still present and remains a non-package file in site-packages
    until a later approved cleanup.

Shim removal conclusion:
  The evidence supports removing the temporary shim AFTER installing
  1.17.3, because:
    (a) only tensorflow_metadata 1.21.0 imports google.protobuf.runtime_version;
    (b) the 1.17.3 wheel has zero such imports;
    (c) the isolated test with runtime_version imports blocked passed.
  However, final removal should be gated on a post-install reversible test
  (rename the shim aside, run the import checks, restore on failure). That
  test is necessary because the isolated test shadowed rather than uninstalled
  1.21.0. No further dependency investigation is required beyond that check.
